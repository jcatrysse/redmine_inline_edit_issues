Major, app/controllers/inline_issues_controller.rb:7-15
Authorization does not cover multi-project selections; cross-project use 403s even when the user has the permission in all involved projects. The before_action :authorize only checks @project; when issues span multiple projects, @project remains nil and ApplicationController#authorize won’t consider @projects (it only uses @project), so a legitimate user cannot open or submit the form across projects.
Failure: On the global Issues page, select issues from two different projects and choose “Edit Inline”. The context menu item is enabled (your code checks User.current.allowed_to?(:issues_inline_edit, @projects)), but GET /inline_issues/edit_multiple (no project_id, multiple projects) responds 403. Likewise, submitting PUT /inline_issues/update_multiple for issues across projects fails 403.
Fix: Add an explicit permission check against all involved projects and remove/reduce reliance on ApplicationController#authorize for these actions, e.g.:
  before_action :authorize_inline_projects, only: [:edit_multiple, :update_multiple]
  def authorize_inline_projects
    projects = @projects.presence || (@project ? [@project] : [])
    raise ::Unauthorized unless projects.present? && User.current.allowed_to?(:issues_inline_edit, projects)
  end
Alternatively, override authorize usage to pass @projects into User.current.allowed_to? directly (ApplicationController#authorize won’t do this).

Resolution: not a defect, the same claim as in openai-2026-10-06-271f7fd.md. Core's
ApplicationController#authorize calls `allowed_to?(..., @project || @projects, ...)` (line 340 of
7.0-stable-GEOxyz), and allowed_to? on an array requires the permission in every project. Proven
for the save by `test_update_multiple_across_projects_without_a_project_in_the_url` and, new, for
the form by `test_edit_multiple_across_projects_with_the_permission_in_each` (issues of projects
1 and 2, no project in the URL: 200 with inputs for both).
