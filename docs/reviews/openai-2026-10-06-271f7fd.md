Major, app/controllers/inline_issues_controller.rb:6-13
update_multiple authorization relies on a single @project/params[:project_id] via authorize, not on each issue’s project. For cross-project posts, authorize can be satisfied by a project where the user has the plugin permission, while issues from another project (where the user lacks the plugin permission) are still processed as long as attributes_editable? (i.e. core edit_issues) is true.
Scenario: User jsmith (Manager in project A with issues_inline_edit; Developer in project B without issues_inline_edit) submits update_multiple with project_id=A and includes an issue from project B in params[:issues]. authorize passes on A, check_attributes_editable passes on B (Developer has edit_issues), and issue in B is updated even though jsmith lacks the plugin permission in B.
Fix: Enforce issues_inline_edit on every target issue’s project before saving. For example, in find_issues_to_update (after @projects/@issues are built) add:
  raise ::Unauthorized unless @projects.all? { |p| User.current.allowed_to?(:issues_inline_edit, p) }
Alternatively, in check_attributes_editable require both issue.attributes_editable? and User.current.allowed_to?(:issues_inline_edit, issue.project) for all @issues.

Resolution: not a defect. For update_multiple, @project is never taken from params[:project_id]
(find_project runs for edit_multiple only); find_issues_to_update sets @projects from the
submitted issues and @project only when they share one project. Core's `authorize` checks
`allowed_to?(..., @project || @projects)`, and allowed_to? on an array requires the permission in
every project. Proven by `test_update_multiple_should_check_the_permission_on_the_project_of_the_issue`
(issue of project B alone, URL project A: 403) and the new
`test_update_multiple_across_projects_should_need_the_permission_in_each_project` (issues of A and
B, URL project A: 403, nothing saved), in the commit after this review.

Major, app/controllers/inline_issues_controller.rb:6-13 and 130-148
Legitimate cross-project updates are incorrectly rejected with 403 when the edit form is posted without a project in the URL (non-nested route) because before_action :authorize is still applied to :update_multiple while @project is nil and params[:project_id] is absent. Redmine’s authorize expects a single project and will deny in this case even if the user has the plugin permission in all involved projects.
Scenario: Manager selects issues across two projects from the list, opens the cross-project inline edit form (non-project URL), and submits. update_multiple runs find_issues_to_update (sets @projects, but not @project) then authorize; authorize evaluates against a nil project and denies with 403. Result: cross-project inline save is impossible even for fully authorized users.
Fix: Do not use authorize for :update_multiple. Instead, rely on explicit checks that already know the target issues:
  - In find_issues_to_update (or a dedicated before_action), after building @issues/@projects, enforce User.current.allowed_to?(:issues_inline_edit, p) for every p in @projects and render 403 if any fails.
  - Keep check_attributes_editable to enforce core edit rights.
This both removes the false 403 and closes the permission bypass above.

Resolution: not a defect. `authorize` does not evaluate a nil project here: with issues of
several projects @projects is set and `allowed_to?` takes the array. The new
`test_update_multiple_across_projects_without_a_project_in_the_url` (permission in both projects,
no project in the URL) saves both issues and redirects, in the commit after this review.
