- Severity: major
  File: app/controllers/inline_issues_controller.rb:~130 (method find_issues_to_update, at Issue.where(:id => issue_ids))
  Problem: params[:issues] keys are taken verbatim as IDs without numeric validation. Passing a non-numeric key (e.g., "abc") makes ActiveRecord build a where(id: ["abc", ...]) which, on PostgreSQL, raises PG::InvalidTextRepresentation (invalid input syntax for integer) and returns a 500 instead of a controlled 4xx.
  Failure scenario: An authenticated user with a valid CSRF token posts to /inline_issues/update_multiple with issues[abc][subject]=X alongside a valid issue. On PostgreSQL 16 this crashes with a 500 error; on MySQL/MariaDB behavior depends on SQL mode (may coerce to 0 or still error), but can still produce an unhandled error.
  Fix: Filter and validate the keys before querying. For example:
    issue_ids_param = params[:issues].respond_to?(:keys) ? params[:issues].keys.map(&:to_s).uniq : []
    issue_ids = issue_ids_param.grep(/\A\d+\z/)
    return render_error(:status => 422) if issue_ids.size != issue_ids_param.size
    @issues = Issue.where(id: issue_ids.map!(&:to_i)).to_a
    raise ActiveRecord::RecordNotFound if @issues.empty? || @issues.size != issue_ids.size

  Resolution: not a defect. ActiveRecord casts the ids to integers before they reach the database
  ("abc" matches no row), so the count check answers 404. The new
  `test_update_multiple_with_an_issue_id_that_is_not_a_number_should_respond_with_404` passes on
  PostgreSQL 16 (7.0-stable) and MariaDB 10.11 (7.0-stable-GEOxyz), in the commit after this review.

- Severity: major
  File: app/controllers/inline_issues_controller.rb: find_projects (used by edit_multiple; unchanged in this diff but relied upon)
  Problem: edit_multiple loads issues from params[:ids] to build @projects/@project, but does not enforce visibility (Issue.visible) on those IDs before rendering the form. As a result, a user with the permission in one project can craft a cross-project edit_multiple URL that includes issues from a private project they cannot see; the form will render those rows as text (not inputs), leaking their subject and other column values.
  Failure scenario: User jsmith (Manager in ecookbook, no membership in a private project) opens /inline_issues/edit_multiple?project_id=ecookbook&ids[]=1&ids[]=<id_of_private_issue>&c[]=subject. The page renders with a row for the private issue showing its subject as text, revealing information the user must not see.
  Fix: In find_projects (and any code that populates @issues for edit_multiple), load through the visibility scope and fail if any submitted ID is not visible:
    issues = Issue.visible.where(id: @ids).to_a
    raise ::Unauthorized if issues.size != @ids.uniq.size
    @issues = issues
    @projects = @issues.map(&:project).uniq
    @project = @projects.first if @projects.size == 1
  Alternatively, silently drop invisible IDs and proceed only with visible ones, but then the menu and UI tests should be adjusted to not leak invisible issues.

  Resolution: not a defect. The rows of the form come from `@query.issues`, and IssueQuery is
  scoped to Issue.visible (and to the project of the URL with its subprojects); find_projects only
  feeds `authorize`, which without a project in the URL requires the permission in the project of
  every id, so a private project's issue gives 403. The new
  `test_edit_multiple_should_not_show_an_issue_the_user_cannot_see` (dlopper, ids of project 1 and
  of the private project 2: no row and no subject with project in the URL, 403 without) passes on
  both databases, in the commit after this review.
